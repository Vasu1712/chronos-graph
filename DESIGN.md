# Design

> Generated by `make report`; the architecture text is extracted from `SPEC.md`, the examples are real
> ingestions run by the report script, and the failure modes are mined from the evaluation outputs.

ChronosGraph is a local, persistent memory for multi-session conversational agents. It remembers what was
said, when it was true in the world, and when the system learned it, and it answers only with claims that a
cited turn entails.

## Architecture

#### 1. Architecture overview

Three tiers:

1. **Tier 1 — Immutable Episodic Log** (source of truth).
2. **Tier 2 — Bi-Temporal Fact and Entity Store**, populated by the **Ingestion Engine**.
3. **Tier 3 — Hybrid Retriever and Provenance-Enforced Generator**.

```
 sessions ──► Tier 1 episodes (append-only) ──► Ingestion Engine ──► Tier 2 memories/entities
                                                                         │
 query ──► Tier 3 query analysis ─► hybrid retrieval ─► temporal filter ─► episodic expansion
            ─► pack ─► answerability gate ─► structured generation ─► verifier ─► answer
```

### Tier one and two: the schema

#### 4. Tier 2 — Bi-Temporal Fact and Entity Store

```
entities(
  entity_id        TEXT PRIMARY KEY,
  conversation_id  TEXT,
  canonical_name   TEXT,
  entity_type      TEXT,
  is_speaker       INT,

)

entity_aliases(entity_id, alias, turn_uid)

  memory_id                 TEXT PRIMARY KEY,

  polarity                  TEXT,   -- POS | NEG

  role         TEXT    -- ASSERTS | REAFFIRMS | CORRECTS | RETRACTS

  query_id              TEXT,

  verifier_json         JSON
)
```

**Vector index:** embeddings are stored as BLOBs and searched with NumPy in memory
(corpora are small).

### Ingestion

#### 3. Ingestion Engine

Runs **in batch at session end**, **one SQLite transaction per session**.

1. **Speaker-aware coreference.** `I/me/my` bind to the turn's speaker; `you/your` bind to the
   other participant in two-party chats. Speakers are registered as entities **before** ingest.
2. **Extraction.** Extract self-contained atomic facts (resolved text, no pronouns), entities
   mentioned, the verbatim quote that supports each fact, and any time expression.
   - The LLM only **normalizes** the time expression (absolute, or relative offset + unit).
   - Python code computes dates from `session_ts` and assigns a precision:
     `DAY | WEEK | MONTH | YEAR | SESSION | BEFORE | UNKNOWN`.
3. **Candidate lookup.**
   - If the fact maps to a closed single-valued attribute key (§3.1), candidates are ACTIVE
     memories with the same subject and `attribute_key`.
   - Otherwise candidates are the **top-5 ACTIVE memories of the same subject** by embedding
     similarity.
4. **Classify against candidates:**
   `NEW | DUPLICATE | EXTENDS | UPDATES | CORRECTS | HISTORICAL | CONFLICT`.
5. **Write** with the bi-temporal rules (§5).

##### 3.1 Closed single-valued attribute keys

Defined in `src/chronos/ontology/attributes.yaml`:

- `residence`
- `hometown`
- `employer`
- `job_title`
- `school`
- `relationship_status`
- `partner`
- `diet`
- `favorite:<category>`
- `primary_tool:<purpose>`

Each key has a description and paraphrase examples shown to the extractor. Anything else has
`attribute_key = NULL` and is **multi-valued**.

### Tier three: retrieval and answering

#### 6. Tier 3 — Hybrid Retriever and Provenance-Enforced Generator

1. **Query analysis** by rules plus entity string matching (**no LLM call**):
   - intent: `CURRENT | AS_OF | HISTORY | TEMPORAL_ORDER | OPEN`
   - subject speaker
   - time constraint resolved to a date
2. **Hybrid retrieval.** Dense + BM25 (FTS5) over `memories.fact_text` and over episodes,
   fused with **Reciprocal Rank Fusion** (`k = 60`).
3. **1-hop expansion** through `fact_entities` from entities named in the query.
4. **Temporal filter by intent:**
   - `CURRENT` = ACTIVE with open `valid_to`.
   - `AS_OF t` = non-retracted facts whose interval contains `t`.
   - `HISTORY` / `TEMPORAL_ORDER` = include version chains with dates.
5. **Episodic expansion.** Fetch each selected memory's source turns plus a ±1 turn window.
6. **Packing** into a token budget (default **1500**); every turn prefixed
   `"[turn_uid | date | speaker]"`.
7. **Answerability gate.** Deterministic speaker-mismatch check, then one LLM call
   "does this evidence answer this exact question?" →
   `ANSWERABLE | PARTIAL | NOT_ANSWERABLE`. Abstain on `NOT_ANSWERABLE`.
8. **Structured generation:**
   `final_answer`, `claims[{text, cited_turn_uids, cited_memory_ids}]`, `abstained`,
   `abstention_reason`.
9. **Verifier, per claim:**
   - cited turns exist;
   - cited turns were in the packed context (checked against `answer_log`);
   - NLI entailment of the claim by the concatenated cited turns.

   Drop failing citations, regenerate once with feedback, drop unsupported claims, abstain if
   none remain.

## Why an episodic log plus versioned facts, and not a full graph

The source of truth is an append-only log of turns. Everything else is derived from it and can be rebuilt.
Facts are rows with intervals, a status and a version chain, each tied to the exact turn and quote that
support it.

- A graph store would add entity-relationship edges, but the questions in these benchmarks are mostly
  answered by a fact about one person at one time. What goes wrong in practice is not the lack of edges;
  it is deciding which of several statements about the same attribute is current. A versioned fact table
  makes that decision explicit, auditable and cheap.
- Edges would also multiply the places an extraction error can hide. A row with a quote can be read and
  checked by a person in seconds; a path through a graph cannot.
- One-hop expansion through the fact-to-entity link table gives the part of a graph that retrieval needs
  (what else is linked to this person) without a graph database.
- The log is immutable (triggers forbid updates and deletes), so a wrong fact can be retracted and
  explained but never silently rewritten. Provenance is a real foreign key, not a list inside a column.

The cost is honest: no multi-hop traversal beyond one step, and relations between entities are recorded
only as mentions, not as typed edges.

## Bi-temporal rules

Two clocks. Event time is when something was true in the world (`valid_from`, `valid_to`, `event_date`),
with a precision (day, week, month, year, session, before, unknown). Transaction time is when the system
learned it (the session and turn at which a row was recorded or retired). The write rules compare event
time at the coarser of the two precisions and fall back to arrival order only when event time cannot
decide.

#### 5. Bi-temporal write rules

Order key = `(session_ordinal, turn_index)`.

| Class | Rule |
|---|---|
| **NEW** | Insert ACTIVE. |
| **DUPLICATE** | Add a `fact_sources` row (`REAFFIRMS`); `corroboration += 1` for a new distinct turn. |
| **EXTENDS** | Insert ACTIVE, keep the old one ACTIVE (adds detail, no conflict). |
| **UPDATES** | Compare event time. If `new.valid_from` is later than `old.valid_from` at the coarser of the two precisions, old becomes SUPERSEDED with `valid_to = new.valid_from`, retired at the new fact's order key, chained via `supersedes_id` / `superseded_by_id`. If the new fact is **earlier**, insert it as SUPERSEDED and link it behind the old one. If **incomparable** (equal at shared precision, or SESSION precision), the later order key wins, so in-session updates work. |
| **CORRECTS** | ("Pune, sorry, I meant Mumbai") Old becomes RETRACTED (never true), new is ACTIVE, source role `CORRECTS`. |
| **HISTORICAL** | ("back in 2019 I lived in Delhi") Insert with its closed interval; never touches the current fact. |
| **CONFLICT** | (same turn, contradictory, no correction cue) Both CONFLICTED with a shared `conflict_set_id`; retrieved and shown together. |
| **NEG polarity** | A NEG fact matching an active fact closes it (SUPERSEDED, `valid_to` from the new evidence). |
| **Idempotence** | Re-ingesting a session is a no-op. |

Examples, produced by ingesting the repository's probes with scripted extractor outputs (so they show the
write rules, not a model's mistakes):

**UPDATES: a later session moves the user; the old value is closed, not deleted** (probe `update_01`)

```
  [2023-01-15] Jordan: Austin has been great, I love living here.
  [2023-01-15] Kim: The tacos alone!
  [2023-05-17] Jordan: Big news, I moved to Seattle last month!
  [2023-05-17] Kim: No way, congrats!

s1t1   SUPERSEDED POS residence        Jordan lives in Austin.  [2023-01-15 (SESSION) -> 2023-04-01 (MONTH)]
s2t1   ACTIVE     POS residence        Jordan moved to Seattle.  [2023-04-01 (MONTH) -> now]
```

**HISTORICAL: a late mention of an old fact never replaces the current one** (probe `late_mention_01`)

```
  [2023-03-05] Rahul: How is the new job treating you?
  [2023-03-05] Priya: Work has been hectic since I settled in Bengaluru.
  [2023-06-10] Rahul: Did you ever live up north?
  [2023-06-10] Priya: Yes, back in 2019 I lived in Delhi for a year, the winters were brutal.

s1t2   ACTIVE     POS residence        Priya lives in Bengaluru.  [2023-03-05 (SESSION) -> now]
s2t2   ACTIVE     POS residence        Priya lived in Delhi in 2019.  [2019-01-01 (YEAR) -> 2019-12-31 (YEAR)]
```

**CORRECTS: 'Pune, sorry, I meant Mumbai' retracts the old value (it was never true)** (probe `correction_01`)

```
  [2023-04-04] Sam: Where are you based these days?
  [2023-04-04] Neha: I live in Pune now.
  [2023-04-04] Sam: Pune, nice!
  [2023-04-04] Neha: Pune, sorry, I meant Mumbai. I always mix them up when I'm tired.

s1t2   RETRACTED  POS residence        Neha lives in Pune.  [2023-04-04 (SESSION) -> now]
s1t4   ACTIVE     POS residence        Neha lives in Mumbai.  [2023-04-04 (SESSION) -> now]
```

**NEG polarity: 'I don't play guitar anymore' closes the matching fact** (probe `neg_01`)

```
  [2023-02-02] Arjun: I play guitar in a little band on weekends.
  [2023-02-02] Mei: What kind of music?
  [2023-06-18] Mei: Still gigging?
  [2023-06-18] Arjun: I don't play guitar anymore, my wrist can't take it.

s1t1   SUPERSEDED POS -                Arjun plays guitar in a band on weekends.  [2023-02-02 (SESSION) -> 2023-06-18 (SESSION)]
s2t2   ACTIVE     NEG -                Arjun no longer plays guitar.  [2023-06-18 (SESSION) -> now]
```

**Event time vs arrival: the earlier move is told later and goes behind the current fact** (probe `out_of_order_01`)

```
  [2023-07-10] Ines: I moved to Austin in June 2022 and still love it.
  [2023-07-10] Paul: Austin suits you.
  [2023-09-02] Paul: Was Austin your first move?
  [2023-09-02] Ines: No, I moved to Denver in March 2021, that was my first big move.

s1t1   ACTIVE     POS residence        Ines moved to Austin.  [2022-06-01 (MONTH) -> now]
s2t2   SUPERSEDED POS residence        Ines moved to Denver.  [2021-03-01 (MONTH) -> 2022-06-01 (MONTH)]
```

A closed attribute vocabulary is what makes supersession reliable: a fact either maps to a single-valued key
such as residence or employer, in which case candidates are looked up by key, or it does not and is
multi-valued. Without the key, deciding that "moved to Seattle" replaces "lives in Austin" rests on
embedding similarity alone.

## Provenance and verification

Every memory has at least one source row naming a turn, a verbatim quote and the character span of that
quote in the turn. At answer time the generator must cite turn ids from the context it was shown. The
verifier then checks, per claim and per citation: the turn exists, it was in this query's packed context
(recorded in the answer log before generation), and an NLI model finds the claim entailed by the
concatenated cited turns at or above a threshold (0.5). Failing citations are dropped; if a claim
loses all of them the answer is regenerated once with feedback naming the unsupported claims; claims still
unsupported are removed; if none remain the system abstains. Whatever is returned is therefore supported
by turns that were in front of the model.

This is evidence that the answer is grounded in the cited text, not proof that the cited text is true, and
the NLI model is itself fallible (see the claim re-check in the evaluation).

## Related work

- **Zep / Graphiti** already maintains a temporal knowledge graph with bi-temporal edges. ChronosGraph's
  bi-temporal facts are not new relative to it.
- **Mem0** already extracts facts and updates them (add, update, delete, no-op) as new information
  arrives. Updating a stored fact is not new either.
- **MemGPT / Letta** manage tiers of memory for an agent; the three-tier split here is in the same spirit
  and differs in what each tier stores.
- **LoCoMo** and **LongMemEval** are the benchmarks used; both are used here as released, with
  LongMemEval's answer-checking prompts.

What this project adds, and what it should be judged on: turn-level citations that are checked by an
entailment model before an answer is returned; a closed attribute vocabulary used to make supersession
reliable; and a complete pipeline that runs locally on a seven-billion-parameter model on a laptop. It has
not been compared with Zep or Mem0 end to end except where the evaluation says so.
